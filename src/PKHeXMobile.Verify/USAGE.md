# Offline desktop parity fixture verifier

This is a **read-only local comparison tool**, not a certified desktop parity suite or Android app. It accepts a manifest next to privately stored, rights-cleared save fixtures and compares the observed projection against a separately authored expected projection. It checks the input SHA-256, reopens the file to detect changed bytes, compares all trainer/party/box projection fields and returns a nonzero exit code for any mismatch or refusal.

```sh
dotnet run --project src/PKHeXMobile.Verify -- --help
dotnet run --project src/PKHeXMobile.Verify -- "/private/fixtures/manifest.json"
```

Manifest version 1 requires `schemaVersion: 1`, `coreVersion: "26.10.18"`, and a nonempty `fixtures` array. Each fixture has a portable relative `path` under the manifest's directory (forward-slash components only; no `..`, symlinks or reparse-point traversal), its exact 64-hex-character `sha256`, and a complete `expected` projection with `coreSaveType`, `gameVersion`, `generation`, `trainerName`, `trainerId`, `secretId`, `partyCount`, `boxCount`, `boxSlotCount`, `party` and `boxes`. Party entries require `slotIndex`, `species`, `nickname`, `level`, `isEgg` and `isShiny`; each box requires `boxIndex` and `occupiedSlots`. Empty boxes must be included as empty arrays; omitted fields are not valid independent evidence.

**Establish expected values independently**, using desktop PKHeX with matching Core **26.10.18** and a separately verified format identity. A baseline copied from this reader or generated by the same Core is a useful regression test but **not independent parity evidence**. Keep real saves, private trainer details, hashes linked to personal files, console keys and manifests out of the public repository. The verifier intentionally prints only fixture numbers and mismatch field paths, not Pokémon or trainer values. No files are written by this tool. The path policy is a read-only hygiene check, not a race-free filesystem sandbox: keep private fixtures in a trusted directory that other processes cannot modify during verification.

Passing comparisons do not certify ROM-hack identity, independent checksums, full desktop feature parity, Android document-provider behavior, or any save-writing capability.

## Detailed projection parity (manifest schema v2)

Use `schemaVersion: 2` with the same pinned `coreVersion: "26.10.18"` to **require** a `details` object for **every occupied party and box slot**. Schema v1 remains supported for older basic-slot baselines, but it does not certify the additional Pokémon fields. Each schema v2 `details` object requires `nature` (Core string), `abilityId`, `heldItemId`, `gender`, `form`, `moves` (four numeric `first`, `second`, `third`, `fourth` IDs), `individualValues` and `effortValues`. Both spreads require numeric `hp`, `attack`, `defense`, `specialAttack`, `specialDefense`, `speed`. Every nested field must be present, including zero. A missing detail object is an explicit mismatch; no value is silently defaulted. The verifier reports field paths only.

Record each expectation independently using the matching desktop PKHeX build and the exact game/generation semantics. In Gen 1–2, Core's IV/EV properties may represent DV/stat experience, not modern per-stat mechanics. A schema v2 PASS demonstrates only the compared read-only projection, not complete legality, format identity, source provenance or write safety. Never derive expected values from this same mobile reader and call the result independent parity.

The synthetic smoke suite mutates each of the 21 detail fields and verifies that every mismatch is detected. It also exercises a synthetic `WA9` clone through an identity-preserving guard: pinned Core's source-level `WA9.Clone()` may return a `WC9` with the wrong game context. That check does not enable Mystery Gift import or saving.

## Typed ribbon, mark and memory subset (manifest schema v3)

Schema v3 requires all v2 detail fields plus an `awards` object for **every occupied Pokémon**. This is deliberately **not complete ribbon parity**. It projects only three typed Gen 9 common ribbons, eight typed Gen 9 marks, raw memory-ribbon counts and presence flags, the affixed ribbon index when supported, and raw OT/HT memory fields when supported.

The `awards` object must include `gen9Flags` (an ordered list of `name` and `owned` objects), `contestMemoryCount`, `battleMemoryCount`, `hasContestMemoryRibbon`, `hasBattleMemoryRibbon`, `affixedRibbon`, `originalTrainerMemory`, and `handlingTrainerMemory`. Every key is mandatory even if its value is JSON `null`. Each non-null trainer memory requires `memory`, `intensity`, `feeling`, and `variable`. Missing, duplicated, unknown or reordered flag names are rejected. Types without the relevant Core interfaces have empty flag lists and null corresponding values; null does not mean the ribbon is absent.

Expected values must be obtained independently from same-version desktop PKHeX to count as parity evidence. A synthetic schema v3 PASS proves only field-comparison logic, not desktop equivalence, game-format certification, Android trimming, legality or write safety.

## National-species Pokédex flag subset (manifest schema v4)

Schema v4 retains all schema v3 fields and requires a non-null `pokedex` object for every fixture. This gate is intentionally limited to saves for which pinned Core reports `HasPokeDex`. The object requires `maxSpeciesId` (Core's national-species scan bound), `seenSpecies` and `caughtSpecies` (strictly ascending unique numeric species IDs between 1 and `maxSpeciesId`, inclusive). Both arrays are mandatory even when empty. A missing, duplicated, out-of-order, out-of-range or mismatched flag fails the comparison. Older schemas do not require dex data.

The projection reads `SaveFile.GetSeen/GetCaught` without invoking setters. **It does not cover regional/DLC mapping, forms, display flags, language flags, gender/shiny histories, research tasks, acquisition side effects or legality.** Do not interpret the denominator as the number of species available in a regional Pokédex. Same-Core synthetic tests are regression checks only; independent desktop-matched fixtures and Android provider/device tests remain outstanding. This schema does not enable save writing.


## Core-enumerated inventory subset (manifest schema v5)

Schema v5 requires schema v4 plus a non-null "inventory" object for fixtures
whose pinned Core save type exposes a nonempty bag. It requires "pouches",
each with "type", "maxCount", "entries". Every entry requires "slotIndex",
"itemId", "count", "coreItemType", "pouchCode", "flags" and "padding".
The three raw fields are null for item types that do not expose them and
all present for InventoryItem9/InventoryItem9a. Zero-count entries are
preserved. The verifier rejects malformed, duplicated or reordered entries.

This is **not a complete raw-block inventory audit**: unknown or out-of-list
item IDs, hack-specific slots, and version-dependent Z-A unlock flags may be
absent from Core's pouch enumeration. The source inventory is never written,
sanitized or sorted. Synthetic SV/ZA item blocks test only the projection,
comparison and presentation. Independent same-version desktop fixtures,
raw-block hashes, layout authentication and Android provider/device tests are
still needed before any claim of parity or save-write safety.

## Core physical storage slot flags (manifest schema v6)

Schema v6 retains all v5 requirements and adds a non-null `storage` object
with `boxes`, containing exactly `boxCount` ordered records. Each box has
`boxIndex` and `slots`; every physical position, including empty positions,
must have `slotIndex`, `rawFlags` (numeric Core StorageSlotSource bits), and
`overwriteProtected` (Core's computed boolean). Counts must match
`boxSlotCount`, indices must be zero-based and ordered, and unreviewed flag
bits or inconsistent protection semantics are rejected. This is a read-only
snapshot of Core's flags, **not** independent validation of battle-team pointers,
slot byte identity, protection enforcement or a write-safe layout.

Use independent same-version desktop observations to establish reference
values. The synthetic storage tests cover flag enumeration, immutable snapshots,
malformed expectations, changed values and read-only Android detail rendering;
they do not certify MoveBox, SwapBox, pointer remapping, real-save parity or
transactional export. All editing and export remain disabled.

## Core trainer scalar subset (manifest schema v7)

Schema v7 retains all schema v6 requirements and adds a non-null
`trainerProgress` object. The object must explicitly contain `genderCode`,
`languageCode`, `money`, `playedHours`, `playedMinutes`,
`playedSeconds`, and `currentBox`. Numeric zero is meaningful and cannot
be substituted for an omitted key. The comparison checks every field and
refuses implausible clock values, language codes and current-box indices.

These are **raw pinned-Core scalar getters**. Some formats inherit virtual
defaults, so zero is not proof that a record exists or has that value.
This is not parity for Gen6 records, fashion, trainer events, Gen9 currencies,
last-saved timestamps, flags, DLC state, or any setter. A matching manifest
must be independently produced with desktop PKHeX Core 26.10.18. Synthetic
tests establish only immutable projection, source-byte preservation and
field-level mismatch detection. Save editing/export remain disabled.


## Schema v8 — training diagnostics (synthetic support only)

For every occupied slot, include `Details.Training` with `coreFormat`, `effectiveEffortTotal`, `conventionalPerStatEffortCeiling`, `conventionalTotalEffortCeiling`, `derivedHpDv`, `coreSpecialGettersAgree`, and `exceedsConventionalEffortLimits`. The classic-only values must be explicit JSON `null` on modern entities. This records pinned-Core raw getter interpretation and flags conventional EV-limit anomalies; it does **not** establish legality or permission to save. Schema v8 also requires all earlier schema fields. Independent same-version desktop expectations remain mandatory before claiming parity.

## Schema v10 — immutable PID, shiny and egg provenance diagnostics

Schema v10 retains every schema v1–v9 requirement and adds `details.identity` for every occupied Pokémon. The mandatory raw fields are `coreFormat`, `originGeneration`, `personalityId`, `encryptionConstant`, `trainerId32`, `shinyXor`, `abilityNumber`, `pidAbility`, `metLocation`, `eggLocation`, `ball`, `metLevel`, `originalTrainerFriendship`, `isEgg`, `wasEgg`, `isShiny`, `metDate` and `eggDate`. Each date has required raw `year`, `month`, `day` and nullable `isoDate` (the last must be present even when null). Dates are raw Core getters, not proof of stored fields: unsupported formats can return virtual defaults; invalid calendar bytes must not be corrected. Locations remain full 16-bit IDs. Shiny XOR is checked against raw ID32/PID, but shiny legality is not inferred from XOR alone. The verifier checks both observed and reference consistency, not independent fixture provenance. These fields do not authorize PID rerolls, egg normalization, location writes or save export. Synthetic regression coverage is not desktop parity evidence.

## Schema v11 — read-only daycare/nursery raw metadata

Schema v11 retains all earlier requirements and requires an explicit `daycare`
object in each fixture's `expected` projection. It contains `available`
and `facilities`. For formats without a reviewed Core nursery interface,
use `{"available":false,"facilities":[]}`; do not omit the object.
Each available facility (one or two, in source order) requires
`facilityIndex`, nullable `eggAvailable`, nullable `seedHex` (8 hex digits for Gen4 32-bit seeds, 16
for 64-bit seeds, 32 for Gen7 UInt128), and one (Gen1) or two (other reviewed generations)
ordered `slots`. Each slot requires `slotIndex`, `occupied`,
`rawLength`, `rawSha256` (64 hex digits) and nullable
`experienceGained`. JSON nulls must be present for unsupported getters.

The source adapter bounds parent memory before hashing; Sword/Shield's
Core nursery indexer otherwise exposes a mutable tail slice. Parent
digests describe **raw Core memory**, not independently decoded species,
validity, legality, or authenticated save layout. Black/White's seed is
reported as null because its Core setter is a no-op; B2W2 exposes 64 bits.
This schema is a comparison protocol, not a claim of independently matched
desktop fixtures. Synthetic tests are not write or device certification.
