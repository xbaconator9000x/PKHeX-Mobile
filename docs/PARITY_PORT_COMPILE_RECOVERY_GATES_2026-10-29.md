## Three smallest implementation tickets (strictly implementation-owned)

1. **P0: isolate hack-only compile dependencies.** Keep PKForge's fork-based build reproducible; implement retail-only official-Core adapter that excludes `SAV8BSLuminescent`, `PB8LUMI`, `EntityContext.Gen8bLumi`, `PersonalTable.BDSPLUMI`, `CompassBlockKeys` from the *retail* compilation unit. Preserve hack source and future profiles separately, and ensure explicit refusal for their layouts. Acceptance: C01–C04 + C05 negative dispatch. No changes to audit-owned docs by implementation agent.
2. **P0: make compatibility result truthful.** Keep diagnostic compilation output visible but add a final failing status or a distinct required compile gate once C03 is expected to pass. Acceptance: C06, including intentionally broken pinned source and forced compiler-error negative test.
3. **P0: reuse existing editor shell for one real vertical slice.** Reuse PKForge UI/editor where rights allow, connect to official-Core detached candidate and existing non-publishing staging, then separate Save As URI. Acceptance: C07–C10, plus P0-01, P0-05, P0-06, P0-08–P0-15 in original gate document. Defer broad editor tabs, AutoMod and hack writes until this path passes.

**Decision boundary:** A green upstream fork build is sufficient to continue *adapting its UI*, not to ship a forked engine as official PKHeX.Core. A failing official-Core engine build is sufficient to block a drop-in swap, **not** a reason to rewrite PKForge's UI from scratch. Preserve the native official-Core read-only app as fallback. The 30 productive-hour target is aspirational; do not trade save integrity for a deadline.
