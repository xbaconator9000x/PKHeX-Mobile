## Architecture and save-safety consequences

**Keep three independent predicates:** (1) authenticated save layout/profile, (2) correctly contextualized per-Pokémon legality, and (3) transactional write permission. Neither `LegalityAnalysis.Valid` nor a clean bulk report implies (1) or (3). A Core checksum-valid save may still be an unsupported ROM-hack layout. No unknown or user-named profile is eligible for vanilla save serialization.

**Legality isolation is a real architectural choice, not a cosmetic settings page.** Official Core exposes mutable static trainer, era, severity, external-checker and encounter-priority state. A future Android editor with tabs, banks and background tasks must serialize context-sensitive work or demonstrate an equivalent safe isolation strategy; run cross-session tests before claiming desktop parity. The first UI implementation can remain strictly read-only and omit legality rather than return misleading uncontextualized results.

**Batch and assist are candidate transactions, not storage transactions.** PKForge's clone-based preview is useful but guards only the current entity bytes at the shown Apply entry point. MAUI's batch path is unsuitable for direct reuse. A future save writer needs a full source revision/identity check, original-byte backup, staged candidate, intended/unintended byte and field diff, independent reparse and safe publication/rollback. Do not adopt an automatic 'legalize' feature as an export authorization bypass.

**Source and asset rights:** PKHeX/Forge/MAUI code remains subject to its own GPL notices and contributor attribution; the Forge NDS12 font is explicitly CC BY-NC-SA 3.0, not automatically GPL-compatible for our intended distribution. No third-party code or assets were imported in this pass. A separate rights manifest and review are mandatory before any import.
