## B. Actual write pipeline and Android failure boundary — priority P0

**PKForge source sequence:** [SafeSaveWriter.cs L105–157](https://github.com/sofianeelhor/PKForge/blob/2df04430e532b78c247f45b936f3068d8f824987/src/PKForge.Infrastructure/SafeSaveWriter.cs#L105-L157) compares candidate to original, validates candidate through the engine, checks layout/slot scope, creates a backup, then calls `access.WriteAtomicallyAsync`. Its [WriteSafety.cs L167–218](https://github.com/sofianeelhor/PKForge/blob/2df04430e532b78c247f45b936f3068d8f824987/src/PKForge.Engine/WriteSafety.cs#L167-L218) compares parsed slots and disallows out-of-scope changes, but is **not** a full byte-level whitelist for all non-slot regions. The upstream [FileBackupService.cs L18–55](https://github.com/sofianeelhor/PKForge/blob/2df04430e532b78c247f45b936f3068d8f824987/src/PKForge.Infrastructure/FileBackupService.cs#L18-L55) writes bytes then metadata sidecar, verifies SHA-256 when a backup is read, and prunes per document.

**Critical distinction:** [AndroidSafFileAccess.cs L24–39](https://github.com/sofianeelhor/PKForge/blob/2df04430e532b78c247f45b936f3068d8f824987/src/PKForge.App/Platforms/Android/AndroidSafFileAccess.cs#L24-L39) implements `WriteAtomicallyAsync` by opening the *existing* SAF URI with `"rwt"`, writing the candidate directly, flushing and closing. Its own comment says SAF lacks a portable rename/swap. The method name does **not** make this a transactional or crash-atomic replacement: provider behavior, interruption after truncation, partial writes and durability have not been proven. [AndroidFolderFileAccess.cs L34–45](https://github.com/sofianeelhor/PKForge/blob/2df04430e532b78c247f45b936f3068d8f824987/src/PKForge.App/Platforms/Android/AndroidFolderFileAccess.cs#L34-L45) likewise overwrites an existing document using `"wt"`. In the inspected `SafeSaveWriter.WriteCoreAsync` there is **no fresh read/hash of the provider document immediately before writing**, no read-back verification afterward, and no catch/restore transaction if the provider write partially succeeds. These are observations about these exact code paths, not a claim that no other PKForge service performs any checks.

**Required implementation ticket P0-IO-01:** default to **Save As new document**, never silently truncate the source. Stage bytes in app-private storage, reopen with a fresh pinned Core, validate identity, block hashes/checksums and intended field/slot diffs, then request a new output document; read back the provider's result and compare exact bytes and hash. If a provider cannot support a verified new-document publication path, fail closed and retain the staged candidate and original. Do not claim arbitrary SAF providers support atomic replace.

**Required implementation ticket P0-IO-02:** for explicit overwrite, verify the current provider bytes against the original fingerprint *just before* any mutation, require a verified independent original-byte backup, and make interrupted overwrite recovery explicit. Test provider revocation, rename/replacement, concurrent editor changes, short write, crash after truncation, no-space and non-seekable descriptors on real Android document providers. Never automatically restore over a document that may have been changed by another actor.

**Required implementation ticket P0-FORMAT-01:** no writing on Gen 3 retail-shape recognition alone. A supported profile must prove exact game/revision, sector map, checksum algorithm, Pokémon encryption, species/move/item tables, slot offsets and optional emulator wrapper; unknown/ambiguous input stays read-only. Compare original and candidate both structurally **and** by allowed byte/block deltas. For unknown hacks, even unchanged round trips alone are insufficient authorization.
